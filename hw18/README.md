## Завдання 1. Виконання та аналіз DNS-запиту (`nslookup` / `dig`)

В командному рядку операційної системи було виконано діагностичну команду для отримання інформації про доменне ім'я `github.com`.

### Команда та її результат:
```bash
nslookup -type=A github.com
```

**Вивід консолі (приклад реального виконання):**
```text
Server:         192.168.1.1
Address:        192.168.1.1#53

Non-authoritative answer:
Name:   github.com
Address: 140.82.121.4
```

Для детальнішого вивчення параметра **TTL (Time To Live)** виконано команду через утиліту `dig`:
```bash
dig github.com A
```

**Вивід консолі (`dig`):**
```text
;; QUESTION SECTION:
;github.com.                    IN      A

;; ANSWER SECTION:
github.com.             60      IN      A       140.82.121.4

;; Query time: 14 msec
;; SERVER: 192.168.1.1#53(192.168.1.1)
```

### Таблиця зафіксованих параметрів DNS-запису:

| Параметр | Значення | Пояснення |
| :--- | :--- | :--- |
| **Доменне ім'я (FQDN)** | `github.com` | Запитуваний ресурс прикладного рівня. |
| **Тип запису** | **A** (Address) | Відображає доменне ім'я в IPv4-адресу. |
| **Отримана IP-адреса** | `140.82.121.4` | Фізична/віртуальна IPv4-адреса хоста `github.com`. |
| **Значення TTL** | **60 секунд** | Час актуальності запису в кеші локального резолвера. |

**Аналіз результату:**  
Значення $TTL = 60 \text{ с}$ є відносно коротким. Це стандартна практика для великих розподілених сервісів (CDN / Load Balancers), яка дозволяє швидко перенаправляти трафік на резервні IP-адреси у випадку відмови одного з серверів або для балансування навантаження.

## Завдання 2. Покроковий розбір послідовності DHCP DORA

При підключенні ноутбука до нової Wi-Fi мережі він ще не має налаштованого IP-інтерфейсу. Для автоматичного отримання мережевої конфігурації виконується 4-кроковий процес **DORA** (Discover $\rightarrow$ Offer $\rightarrow$ Request $\rightarrow$ Acknowledge).

```
Ноутбук (Клієнт)                                     DHCP-сервер
  [ 0.0.0.0 ]                                       [ 192.168.1.1 ]
       |                                                  |
       |-------- 1. DISCOVER (Broadcast 255.255.255.255) ->|
       |<------- 2. OFFER (Unicast/Broadcast) ------------|
       |-------- 3. REQUEST (Broadcast 255.255.255.255)  ->|
       |<------- 4. ACKNOWLEDGE (Unicast/Broadcast) ------|
       |                                                  |
```

### Детальна характеристика кожного кроку:

1. **DISCOVER (Виявлення):**
   * **Відправник:** Ноутбук (IP: `0.0.0.0`, MAC: `AA:BB:CC:DD:EE:FF`).
   * **Отримувач:** Широкомовна адреса (IP: `255.255.255.255`, MAC: `FF:FF:FF:FF:FF:FF`).
   * **Суть кроку:** Ноутбук надсилає пакет UDP (порт джерела 68, порт призначення 67) на всю локальну мережу із запитом: *"Чи є в цій мережі DHCP-сервер? Мені потрібна мережева конфігурація."*

2. **OFFER (Пропозиція):**
   * **Відправник:** DHCP-сервер (IP: `192.168.1.1`, MAC: `00:11:22:33:44:55`).
   * **Отримувач:** Ноутбук (через MAC-адресу `AA:BB:CC:DD:EE:FF` або Broadcast `255.255.255.255`).
   * **Суть кроку:** Сервер резервує вільну IP-адресу і надсилає пропозицію: *"Я пропоную тобі IP `192.168.1.105`, Маску `255.255.255.0`, Шлюз `192.168.1.1`, DNS `192.168.1.1` та термін оренди (lease time) 24 години."*

3. **REQUEST (Запит):**
   * **Відправник:** Ноутбук (IP: `0.0.0.0`, MAC: `AA:BB:CC:DD:EE:FF`).
   * **Отримувач:** Широкомовна адреса (IP: `255.255.255.255`).
   * **Суть кроку:** Ноутбук публічно оголошує про вибір пропозиції: *"Я приймаю пропозицію IP `192.168.1.105` саме від DHCP-сервера `192.168.1.1`"*. Повідомлення відправляється широкомовно, щоб інші можливі DHCP-сервери в мережі зрозуміли, що їхні пропозиції відхилено, і зняли резервацію зі своїх адрес.

4. **ACKNOWLEDGE (Підтвердження):**
   * **Відправник:** DHCP-сервер (IP: `192.168.1.1`, MAC: `00:11:22:33:44:55`).
   * **Отримувач:** Ноутбук (MAC: `AA:BB:CC:DD:EE:FF` / IP: `192.168.1.105`).
   * **Суть кроку:** Сервер фіксує прив'язку IP-адреси до MAC-адреси в таблиці оренди і надсилає фінальне підтвердження: *"Адресу `192.168.1.105` офіційно закріплено за тобою на 24 години"*. Після цього ноутбук налаштовує свій мережевий інтерфейс.

## Завдання 3. Аналіз та спростування помилкового твердження

### Помилкове твердження:
> *"HTTP-запит GET використовується для надсилання форми реєстрації користувача на сервер."*

### Пояснення, чому це твердження є ГРУБОЮ ПОМИЛКОВОЮ:

1. **Порушення безпеки та конфіденційності (Security):**
   * Метод `GET` передає всі параметри (логін, пароль, email, персональні дані) безпосередньо в URL-рядку у вигляді Query Parameters (наприклад: `http://example.com/register?user=john&password=Secret123`).
   * **Наслідки:** URL-рядок із відкритим паролем зберігається в історії браузера, логах веб-сервера (access logs), проксі-серверах, а також передається в заголовку `Referer` при переході на інші ресурси.

2. **Порушення семантики та ідемпотентності методів HTTP:**
   * Згідно зі специфікацією RFC 9110, метод `GET` є **безпечним (safe)** та **ідемпотентним (idempotent)**. Він призначений виключно для *отримання/читання* даних із сервера і не повинен змінювати внутрішній стан системи.
   * Реєстрація користувача — це дія, яка створює новий ресурс у базі даних (змінює стан сервера).

3. **Обмеження на обсяг даних:**
   * Метод `GET` не має тіла запиту (Request Body). Дані в URL мають суворе обмеження за довжиною (залежно від браузера та сервера — зазвичай до 2048–8192 байт). Передача фотографії профілю або великих форм через `GET` неможлива.

### Правильне рішення:
Для надсилання форми реєстрації необхідно використовувати метод **`POST`**.
* Дані передаються у **тілі запиту (Request Body)** у зашифрованому/структурованому вигляді (`application/x-www-form-urlencoded` або `application/json`).
* Метод `POST` не занотовує секретні дані у URL-логи та призначений саме для операцій створення нових ресурсів на сервері.

## Відповіді на контрольні запитання лекції

1. **Чим клієнт-серверна модель відрізняється від P2P?**  
   *Відповідь:* У клієнт-серверній моделі ролі чітко розмежовані: сервер очікує і надає службу, а клієнт ініціює запит. У P2P (Peer-to-Peer) кожен вузол (пір) одночасно виконує функції і клієнта, і сервера, а ресурси розподілені між учасниками без єдиного центру.

2. **Опишіть послідовність викликів сокетного інтерфейсу на сервері.**  
   *Відповідь:* `socket()` (створення) $\rightarrow$ `bind()` (прив'язка до IP/порту) $\rightarrow$ `listen()` (перехід у режим очікування) $\rightarrow$ `accept()` (прийняття з'єднання) $\rightarrow$ `recv()` / `send()` (обмін даними) $\rightarrow$ `close()` (закриття).

3. **У чому різниця рекурсивного й ітеративного DNS-запиту?**  
   *Відповідь:* При *рекурсивному* запиті клієнт делегує виконання резолверу і чекає на кінцеву відповідь (IP або помилка). При *ітеративному* запиті сервер повертає лише підказку (адресу наступного DNS-сервера в ієрархії), а резолвер сам послідовно опитує кожен рівень (корінь $\rightarrow$ TLD $\rightarrow$ авторитетний).

4. **Що означають чотири кроки DHCP (DORA)?**  
   *Відповідь:* **D**iscover (пошук сервера клієнтом), **O**ffer (пропозиція адреси сервером), **R**equest (запит обраної адреси клієнтом), **A**cknowledge (підтвердження та надання лізингу сервером).

5. **Як HTTPS забезпечує безпеку поверх HTTP?**  
   *Відповідь:* HTTPS загортає звичайні текстові HTTP-повідомлення в захищений протокол криптографічного рівня **TLS** (Transport Layer Security). Це забезпечує асиметричне/симетричне шифрування (конфіденційність), перевірку цілісності даних (HMAC) та автентифікацію сервера за допомогою цифрових сертифікатів.

6. **Чому помилка резолву DNS може виглядати як недоступність усього сервісу?**  
   *Відповідь:* Оскільки веб-браузер або застосунок не може перетворити доменне ім'я в IP-адресу (помилка `NXDOMAIN` / `getaddrinfo failed`), він навіть не знає, на яку IP-адресу надсилати TCP-пакет `SYN`. Сам веб-сервер при цьому може бути повністю справним та доступним за прямою IP-адресою.

7. **Опишіть кроки ітеративного резолвінгу від кореневого сервера до авторитетного.**  
   *Відповідь:* 1) Клієнт шле рекурсивний запит до Резолвера; 2) Резолвер шле ітеративний запит до Корня (`.`), Корень повертає адреси TLD-серверів (наприклад, `.ua`); 3) Резолвер шле запит до TLD-сервера, той повертає адресу авторитетного сервера для `example.ua`; 4) Резолвер шле запит до Авторитетного сервера, який повертає підтверджений A-запис (IP-адресу); 5) Резолвер передає відповідь Клієнту.

8. **Що відбувається під час поновлення оренди DHCP (Lease Renewal) і чому воно не потребує повторного Discover?**  
   *Відповідь:* На половині терміну оренди ($T1 = 50\%$) клієнт надсилає точковий **Unicast** запит `DHCP Request` безпосередньо тому серверу, який видав IP-адресу. Оскільки адреса сервера та бажана IP вже відомі, широкомовний пошук `Discover` непотрібний. Сервер відповідає `ACK`, продовжуючи лізинг.

9. **Чим відрізняються коди стану 401 і 403, а також 502 і 503?**  
   *Відповідь:* 
   * `401 Unauthorized` — користувач не автентифікований (відсутні логи/токени); `403 Forbidden` — користувач автентифікований, але не має прав доступу до даного ресурсу.
   * `502 Bad Gateway` — проксі/шлюз (наприклад, Nginx) отримав неправильну відповідь від бэкенд-сервера; `503 Service Unavailable` — сам сервер тимчасово не здатний обробити запит через перевантаження або технічне обслуговування.
