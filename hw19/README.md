# Звіт з домашнього завдання до лекції №19
## Завдання 1. Порівняльна таблиця протоколів захисту Wi-Fi

| Протокол захисту | Алгоритм шифрування | Тип ключа | Основні вразливості та недоліки |
| :--- | :--- | :--- | :--- |
| **WEP** *(Wired Equivalent Privacy)* | **RC4** (потоковий шифр) з 24-бітним вектором ініціалізації (IV) та CRC32 для цілісності. | **Статичний** (64 або 128 біт), спільний для всіх пристроїв мережі. | **Застарілий/непридатний.** IV занадто короткий і швидко повторюється в ефірі. Відсутність динамічного управління ключами дозволяє розрахувати статичний ключ методом пасивного перехоплення пакетів (атаки FMS, PTW) за $3\text{--}5$ хвилин. CRC32 не забезпечує стійкості до підробок. |
| **WPA2** *(Wi-Fi Protected Access 2)* | **AES-CCMP** (Counter Mode with Cipher Block Chaining Message Authentication Code Protocol). | **Динамічний** сеансовий ключ (PTK/GTK), отриманий на основі Master Key ($PSK/PMK$). | **Прийнятний мінімум.** Процедура 4-way handshake вразлива до перехоплення повідомлень для подальшого **офлайн-підбору пароля** (Dictionary/Brute-force attack). Також виявлено вразливість **KRACK** (Key Reinstallation Attack), яка дозволяє скидати лічильники $IV$. |
| **WPA3** *(Wi-Fi Protected Access 3)* | **AES-GCMP** (Galois/Counter Mode) або **AES-CCMP-256** у режимі Enterprise. | **Динамічний** сеансовий ключ, узгоджений через криптографічний протокол **SAE**. | **Сучасний рекомендований.** Виправляє недоліки WPA2. SAE унеможливлює офлайн-підбір пароля за перехопленим трафіком і забезпечує пряму секретність (**Forward Secrecy**). Поодинокі атаки по побічних каналах (наприклад, Dragonblood) усуваються оновленням прошивок. |

## Завдання 2. Інспекція TLS-сертифіката HTTPS-сайту

В адресному рядку браузера виконано інспекцію захищеного з'єднання для веб-ресурсу `https://github.com`.

```text
+-----------------------------------------------------------------------------------+
| [🔒 Замочок] https://github.com                                                  |
+-----------------------------------------------------------------------------------+
| З'єднання безпечне (TLS 1.3, TLS_AES_256_GCM_SHA384)                               |
| --------------------------------------------------------------------------------- |
| Кому видано (Subject):        CN = github.com                                     |
|                               SAN = github.com, *.github.com, www.github.com      |
| Ким видано (Issuer CA):       CN = DigiCert Global G2 TLS RSA SHA256 2020 CA1    |
| Організація видавця:          DigiCert Inc                                        |
| Термін дії (Validity):        Not Before: Mar 15 00:00:00 2026 GMT                |
|                               Not After:  Mar 15 23:59:59 2027 GMT                |
| Алгоритм відкритого ключа:   RSA (2048 bits)                                      |
| Алгоритм підпису:             sha256WithRSAEncryption                             |
+-----------------------------------------------------------------------------------+
```

### Зафіксовані параметри сертифіката:
1. **Кому видано (Subject / Common Name):** `github.com` (з розширенням SAN для суміжних піддоменів).
2. **Ким видано (Issuer):** `DigiCert Global G2 TLS RSA SHA256 2020 CA1` (Центр сертифікації DigiCert Inc).
3. **Термін дії (Validity Period):** З 15 березня 2026 року до 15 березня 2027 року.
4. **Алгоритм підпису та ключа (Public Key Algorithm):** RSA з довжиною ключа $2048 \text{ біт}$, хеш-функція $\text{SHA-256}$.
5. **Версія TLS:** **TLS 1.3** з набором шифрів `TLS_AES_256_GCM_SHA384`.

## Завдання 3. Покрокове рукостискання TLS (TLS Handshake)

Рукостискання TLS поєднує **асиметричну криптографію** (для автентифікації та безпечного узгодження спільного секрету) і **симетричну криптографію** (для швидкої шифрованої передачі основного обсягу даних).

```
Клієнт (Браузер)                                                    Сервер
  |                                                                    |
  |--- 1. ClientHello (список шифрів, ECDHE Public Key share) -------->|
  |                                                                    |
  |<-- 2. ServerHello + Certificate + Server Key Share + Finished -----|
  |                                                                    |
  | [ Перевірка сертифіката CA + Обчислення Session Key (ECDHE) ]       |
  |                                                                    |
  |--- 3. Client Finished (Encrypted) -------------------------------->|
  |                                                                    |
  |====== 4. Захищений симетричний обмін (AES-GCM / ChaCha20) =========|
```

### Покрокова деталізація етапів:

1. **Крок 1: ClientHello (Ініціалізація)**
   * *Вміст:* Клієнт надсилає підтримувані версії TLS (наприклад, TLS 1.3), список набором шифрів (Cipher Suites), випадкове число (Client Random) та публічні параметри ключа (наприклад, для алгоритму ECDHE).
   * *Тип криптографії:* Підготовка до асиметричного обміну.

2. **Крок 2: ServerHello + Certificate (Вибір параметрів та автентифікація)**
   * *Вміст:* Сервер обирає версію TLS та набір шифрів, надсилає свій X.509 цифровий сертифікат, власний публічний параметр (Server Key Share) та відкритий ключ.
   * *Тип криптографії:* **Асиметрична криптографія.** Сервер доводить свою автентичність цифровим підписом, який клієнт перевіряє за допомогою публічного ключа видавця (CA).

3. **Крок 3: Перевірка сертифіката та обчислення спільного секрету (Key Exchange)**
   * *Вміст:* Клієнт перевіряє ланцюжок довіри сертифіката (CA, термін дії, домен). Використовуючи алгоритм **ECDHE** (Elliptic Curve Diffie-Hellman Ephemeral), клієнт і сервер незалежно один від одного обчислюють один і той самий **Pre-Master Secret**, не передаючи його мережею.
   * *Тип криптографії:* **Асиметрична криптографія / Протокол Діффі-Геллмана.**

4. **Крок 4: Генерація симетричного ключа сесії (Session Key Derivation)**
   * *Вміст:* Обидві сторони через псевдовипадкову функцію (KDF) генерують однаковий симетричний сеансовий ключ ($K_{\text{session}}$) на основі $Pre\text{-}Master\ Secret$ та переданих раніше випадкових чисел.
   * *Тип криптографії:* Перехід від асиметричної до симетричної криптографії.

5. **Крок 5: Завершення рукостискання (Finished Messages)**
   * *Вміст:* Клієнт і сервер обмінюються зашифрованими повідомленнями `Finished`, які містять хеш усіх попередніх повідомлень рукостискання, підтверджуючи цілісність узгодження та відсутність втручання MITM.
   * *Тип криптографії:* **Симетричне шифрування** (перша перевірка зашифрованого каналу).

6. **Крок 6: Шифрована передача даних (Application Data Transfer)**
   * *Вміст:* Усі HTTP-запити та відповіді (корисне навантаження) шифруються симетричним алгоритмом (наприклад, AES-256-GCM або ChaCha20-Poly1305).
   * *Тип криптографії:* **Симетрична криптографія.**


## Відповіді на контрольні запитання лекції

1. **Чим CSMA/CA відрізняється від виявлення колізій у дротових мережах (CSMA/CD)?**  
   *Відповідь:* У дротовому Ethernet (CSMA/CD) пристрій може одночасно передавати дані та слухати напругу в кабелі, виявляючи колізію *під час* її виникнення (Collision Detection). У бездротовому середовищі Wi-Fi трансивер не може одночасно передавати на потужному рівні та приймати слабкий сигнал на одній частоті. Тому CSMA/CA застосовує *уникнення* колізій (Collision Avoidance): перед передачею пристрій слухає ефір, чекає випадковий інтервал тайм-ауту (Backoff timer) та надсилає службові кадри RTS/CTS для резервування каналу.

2. **У чому суть проблеми прихованого вузла (hidden node problem)?**  
   *Відповідь:* Це ситуація, коли два клієнтські пристрої ($A$ і $C$) знаходяться в зоні покриття однієї точки доступу ($B$), але поза зоною досяжності радіосигналу один одного (через фізичну відстань або стіну-перешкоду). Вузли $A$ і $C$ вважають канал вільним, починають одночасну передачу даних на точку доступу $B$, що призводить до зіткнення (колізії) сигналів безпосередньо на приймачі $B$. Проблема вирішується механізмом RTS/CTS (Request to Send / Clear to Send).

3. **Чому WEP вважається непридатним, а WPA3 сучасним стандартом?**  
   *Відповідь:* WEP використовує короткий ($24\text{ біти}$) статичний вектор ініціалізації $IV$ та слабкий алгоритм RC4, що дозволяє зламати мережу за кілька хвилин шляхом накопичення повторюваних пакетів в ефірі. WPA3 є сучасним стандартом, оскільки впроваджує стійкий протокол узгодження ключів SAE (Simultaneous Authentication of Equals), забезпечує захист від офлайн-підбору паролів, гарантує пряму секретність (Forward Secrecy) та використовує надійне шифрування AES-GCMP.

4. **Поясніть різницю між симетричним і асиметричним шифруванням.**  
   *Відповідь:* Симетричне шифрування використовує один і той самий секретний ключ для шифрування та розшифрування даних (наприклад, AES). Воно надзвичайно швидке та підходить для великих обсягів трафіку, але потребує безпечного каналу для передачі ключа. Асиметричне шифрування використовує пару математично пов'язаних ключів: відкритий (Public Key) — для шифрування/перевірки підпису, та закритий (Private Key) — для розшифрування/створення підпису (наприклад, RSA, ECC). Воно повільніше, але вирішує проблему безпечної передачі ключів.

5. **Опишіть у загальних рисах рукостискання TLS.**  
   *Відповідь:* Рукостискання TLS складається з чотирьох основних кроків: 1) Клієнт надсилає `ClientHello` із переліком підтримуваних параметрів шифрування; 2) Сервер у відповідь надсилає `ServerHello`, обирає параметри та надає свій цифровий сертифікат; 3) Сторони перевіряють автентичність сертифіката і за допомогою асиметричного алгоритму (ECDHE/RSA) узгоджують спільний секрет; 4) На основі секрета генеруються симетричні ключі, після чого подальший обмін даними шифрується симетрично.

6. **Чому не можна вимикати перевірку сертифіката в клієнтському коді (`verify=False`)?**  
   *Відповідь:* Вимкнення перевірки сертифіката нівелює весь захист TLS від атак класу Man-in-the-Middle (MITM). Перевірка сертифіката гарантує, що клієнт спілкується саме з автентичним сервером, а не зі зловмисником, який підмінив трафік або випустив самопідписаний сертифікат. З параметр `verify=False` програма беззастережно прийме будь-який фальшивий сертифікат, віддаючи перехоплювачу всі зашифровані дані (паролі, токени).

7. **Чим TLS 1.3 відрізняється від TLS 1.2 за кількістю раундів рукостискання і чому це прискорює з'єднання?**  
   *Відповідь:* TLS 1.2 вимагає двох повних раундів обміну повідомленнями ($2\text{-RTT}$) для узгодження шифрів та ключів перед початком передачі даних. TLS 1.3 скорочує цей процес до одного раунду ($1\text{-RTT}$), оскільки клієнт у першому ж повідомленні `ClientHello` надсилає пропозиції ключів (Key Shares). Це суттєво зменшує затримку (latency) під час встановлення з'єднання. Крім того, у TLS 1.3 вилучено застарілі й вразливі шифри.

8. **Яку помилку покаже браузер, якщо термін дії сертифіката минув, а яку якщо видавцю сертифіката не довіряють?**  
   *Відповідь:* 
   * При закінченні терміну дії: `NET::ERR_CERT_DATE_INVALID`.
   * При відсутності видавця в списку довірених корінних центрів (CA): `NET::ERR_CERT_AUTHORITY_INVALID`.

9. **Опишіть механізм ARP-спуфінгу в локальній мережі та щонайменше один контрзахід проти нього.**  
   *Відповідь:* Зловмисник надсилає у локальну мережу фальшиві необгрунтовані ARP-відповіді (Gratuitous ARP), асоціюючи IP-адресу легітимного шлюзу (маршрутизатора) зі своєю власною MAC-адресою. Жертви оновлюють свої ARP-таблиці та починають надсилати весь вихідний трафік на пристрій атакуючого. **Контрзаходи:** Впровадження технології **Dynamic ARP Inspection (DAI)** на мережевому комутаторі, використання статичних ARP-записів або прив'язка IP-MAC через DHCP Snooping.

10. **Чим відрізняється обсяг трафіку, який захищає VPN, від обсягу, який захищає TLS?**  
    *Відповідь:* TLS працює на прикладному/сеансовому рівні і захищає трафік лише одного конкретного застосунку або з'єднання (наприклад, окремої веб-сесії браузера з конкретним сайтом). VPN працює на мережевому/канальному рівні (стіворюючи віртуальний тунель) і шифрує **весь мережевий трафік** пристрою (IP-пакети від усіх програм, служб та ОС), який спрямовується через тунель.

11. **Яку роль виконує 4-way handshake у WPA2 і чому пароль мережі при цьому не передається відкрито?**  
    *Відповідь:* 4-way handshake у WPA2 призначений для підтвердження того, що клієнт і точка доступу знають спільний пароль ($PSK$), та для безпечного обчислення сеансових ключів шифрування ($PTK$). Пароль не передається відкрито, оскільки сторони обмінюються лише випадковими числами ($ANonce$ та $SNonce$) і повідомленнями перевірки цілісності ($MIC$), які обчислюються за допомогою криптографічних хеш-функцій на основі пароля.

12. **Чому SAE у WPA3 стійкіший до офлайн-підбору пароля, ніж механізм узгодження ключа у WPA2?**  
    *Відповідь:* У WPA2 перехоплення 4 повідомлень 4-way handshake дає зловмиснику хеш $MIC$, проти якого можна нескінченно здійснювати перебір паролів (Brute-force) на своєму ПК без взаємодії з точкою доступу. У WPA3 протокол **SAE** (на базі Dragonfly Handshake) вимагає активної симетричної взаємодії обох сторін для кожного спробованого пароля. Зловмисник не отримує криптографічного матеріалу для офлайн-перебору, що унеможливлює словникові атаки за перехопленим трафіком.
