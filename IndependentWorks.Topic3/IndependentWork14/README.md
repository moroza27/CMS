### Завдання 1. Картка TLS-сертифіката веб-сайту

Для аналізу обрано медійний новинний веб-ресурс **Ukrinform** (`ukrinform.ua`). Дані знято з панелі інспектування безпеки з'єднання браузера (Security / Certificate Viewer):

| Поле сертифіката | Значення з сайту |
| ----- | ----- |
| **Домен (Subject / SAN)** | `*.ukrinform.ua`, `ukrinform.ua` |
| **Видавець (Issuer)** | `GTS CA 1C3` (Google Trust Services) |
| **Термін дії (Validity)** | від `2026-08-10` до `2026-11-08` (90 днів) |
| **Версія TLS** | `TLS 1.3` (Шифр: `AEAD_AES_128_GCM_SHA256`) |

*Опис підтвердження:* У браузері біля адреси сайту `https://www.ukrinform.ua` відображається значок «замка», що свідчить про успішне встановлення шифрованого HTTPS-з'єднання та дійсність TLS-сертифіката.

### Завдання 2. Етапи рукостискання TLS 1.3 та перевірка сертифіката

Згідно зі специфікацією **TLS 1.3 (RFC 8446)**, процес рукостискання скорочено до 1 раунду (1 RTT) і складається з наступних кроків:

1. **ClientHello:** Браузер надсилає серверу список підтримуваних криптографічних наборів (cipher suites), версію TLS, ідентифікатор сайту SNI (Server Name Indication) та свій відкритий ключ для алгоритму ECDHE.
2. **ServerHello + Certificate + Key Share:** Сервер обирає сумісний алгоритм шифрування, надсилає свій відкритий ключ, а також зашифрований цифровий сертифікат для автентифікації.
3. **Перевірка сертифіката браузером:** Клієнт виконує комплексну валидацію отриманого сертифіката за такими критеріями:
   * **Відповідність домену:** Перевірка збігу введеної URL-адреси з полем `Subject Alternative Name (SAN)` сертифіката.
     * *Помилка при невідповідності:* `NET::ERR_CERT_COMMON_NAME_INVALID` (або `SSL_ERROR_BAD_CERT_DOMAIN`).
   * **Термін дії:** Перевірка поточного системного часу на належність до інтервалу `Not Before` — `Not After`.
     * *Помилка при протермінуванні:* `NET::ERR_CERT_DATE_INVALID` (або `SEC_ERROR_EXPIRED_CERTIFICATE`).
   * **Довіра до видавця:** Побудова ланцюжка довіри (Chain of Trust) від сертифіката сайту через проміжні CA до кореневого сертифіката (Root CA), що міститься у сховищі довірених сертифікатів ОС/браузера.
     * *Помилка при відсутності довіри:* `NET::ERR_CERT_AUTHORITY_INVALID` (або `SEC_ERROR_UNKNOWN_ISSUER`).
4. **Підтвердження та шифрований обмін:** Після успішної перевірки обидві сторони обчислюють спільний симетричний ключ сеансу (Session Key) і переходять до зашифрованого обміну даними (HTTP/2 або HTTP/3).

### Завдання 3. Аналіз сценарію атаки

**Сценарій:** Скомпрометований публічний Wi-Fi роутер, що підмінює трафік (Man-in-the-Middle / Traffic Injection).

* **Суть атаки:** Зловмисник, захопивши контроль над публічною бездротовою точкою доступу (наприклад, у кафе чи аеропорту), виконує перехоплення та модифікацію незашифрованого мережевого трафіку користувачів. Роутер здійснює підміну DNS- відповідей, модифікує незахищені HTTP-пакети на льоту, вставляє шкідливі JavaScript-скрипти, рекламні банери або намагається здійснити SSL Stripping (примусове зниження протоколу з HTTPS до HTTP).
* **Порушена властивість CIA:** Атака безпосередньо порушує **Целісність (Integrity)** даних (через незаконне модифікування вмісту сторінок та перехоплених пакетів), а також **Конфіденційність (Confidentiality)** (через прослуховування незахищеного трафіку).
* **Контрзаходи:**
  1. **Примусове використання HSTS (HTTP Strict Transport Security) з Preloading:** Налаштування веб-сервера для видачі заголовка `Strict-Transport-Security`. Браузер запам'ятовує, що до сайту слід звертатися **виключно через HTTPS**, автоматично відхиляючи спроби з'єднання через HTTP та блокуючи будь-які сповіщення про підробку TLS-сертифіката без можливості їх ігнорування користувачем.
  2. **Використання зашифрованого VPN-тунелю:** Запуск VPN-клієнта на пристрої користувача при підключенні до ненадійних Wi-Fi мереж. VPN шифрує **весь** IP-трафік пристрою ще до його потрапляння на Wi-Fi роутер, роблячи модифікацію чи читання пакетів скомпрометованим роутером неможливим.
  3. **Використання Secure DNS (DNS over HTTPS / DoH або DNS over TLS / DoT):** Унеможливлює підміну DNS-запитів зламаним роутером шляхом шифрування звернень до DNS-сервера.

### Завдання 4. Порівняльна таблиця TLS та VPN

| Критерій | TLS (Transport Layer Security) | VPN (Virtual Private Network) |
| ----- | ----- | ----- |
| **Обсяг шифрування (Що шифрується)** | Шифрує **лише одне окреме з'єднання** між конкретним застосунком (наприклад, браузером) та веб-сервером на прикладному/транспортному рівні (L7/L4). | Шифрує **весь мережевий трафік пристрою** на мережевому/канальному рівні (L3/L2) до VPN-шлюзу. |
| **Типовий сценарій використання** | Безпечний перегляд веб-сайтів (HTTPS), захист передачі авторизаційних даних, банківських транзакцій та API-запитів у мережі Інтернет. | Захист усіх комунікацій пристрою в незахищених публічних Wi-Fi мережах, безпечний віддалений доступ до внутрішніх ресурсів корпоративної мережі компанії. |

### Відповіді на контрольні запитання

1. **Які поля сертифіката перевіряє браузер під час TLS-з'єднання?**
   Браузер перевіряє:
   * `Subject Alternative Name (SAN)` / `Common Name (CN)` — на відповідність доменному імені сайту;
   * `Validity Period` (`Not Before`, `Not After`) — на чинність за часом;
   * `Issuer` та ланцюжок цифрових підписів — на довіру до видавця (Root CA / Intermediate CA);
   * Статус відкликання сертифіката через протоколи **OCSP** або списки **CRL**.

2. **Яку помилку покаже браузер при невідповідності домену сертифіката?**
   Браузер відобразить помилку **`NET::ERR_CERT_COMMON_NAME_INVALID`** (у Google Chrome / Microsoft Edge) або **`SSL_ERROR_BAD_CERT_DOMAIN`** (у Mozilla Firefox).

3. **Чим VPN відрізняється від TLS за обсягом захищеного трафіку?**
   **TLS** захищає трафік лише однієї конкретної сесії між конкретною програмою та сервером (наприклад, тільки HTTPS-запит браузера). **VPN** створює захищений тунель для абсолютно всього IP-трафіку пристрою (включаючи фонові служби ОС, месенджери, поштові клієнти та інші програми).
